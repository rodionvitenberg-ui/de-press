# ADR 0022: Терапевтический контур — каталог, сессии со статусами, Solana Pay без процессинга

Дата: 2026-08-30
Статус: принято

## Контекст

Часть пользователей просит платные сессии с терапевтами. Вводить полноценный
платёжный процессинг (эквайринг, подписки, споры, KYC) платформа не может и
не хочет: это лицензии, хранение платёжных данных и новый класс рисков — при
том что платформа позиционируется как некоммерческая и анонимная
(PRIVACY.md). При этом есть проверенный некастодиальный паттерн (ADR-0020):
деньги ходят только кошелёк → кошелёк, платформа не держит ключей. Также есть
живой 1:1 канал сессии — диалог с текстом и звонком (ADR-0021).

Терапевт — не Helper (ADR-0010): другая роль, другой поток (инвайт админа,
тариф, подтверждение оплаты), отдельная поверхность.

## Решение

- **Терапевт — отдельная роль по инвайту.** `TherapistProfile` с
  одноразовым invite-токеном, который генерирует Django admin; токен
  активирует профиль через `POST /therapy/claim`. Открытой саморегистрации
  нет.
- **Бэкенд — только статусы и ссылки.** Модель `TherapySession` хранит
  клиента, терапевта, цену и статус: `awaiting_payment → payment_claimed →
  paid → done`, плюс `declined`. Никаких сумм в пути, балансов, попыток
  списания.
- **Платёж — прямой перевод клиент → терапевт** (Solana Pay: deeplink
  `solana:<addr>?amount=…` + QR; адрес и тариф — публичные поля профиля).
  Платформа не участвует в переводе и не может его верифицировать, поэтому
  **оплату подтверждает вручную терапевт** (`payment_claimed` после «Я
  оплатил» → `paid` по решению терапевта; возможен `declined`).
  Идемпотентность: `confirm` из любого «оплачиваемого» статуса не создаёт
  вторую сущность.
- **Псевдонимность.** Клиент в сессии виден терапевту как `client_label` —
  его собственный опциональный псевдоним (или общее «клиент»), не как
  идентичность; ``DialogueSource.THERAPY`` помечает происхождение диалога,
  сам диалог — обычный Initiated Dialogue со звонком.
- **Поверхности.** Публичный каталог активных профилей
  (`GET /therapy/profiles`), запрос сессии авторизованным клиентом, кабинеты
  обеих сторон (`GET /me/therapy/sessions`, `GET /me/therapy/inbox`),
  действия терапевта `confirm|decline|complete`. Клиент может быть
  анонимным (anon-cookie) — терапевту это не раскрывается сверх
  `client_label`.
- **ADR-0020 не задет**: фонд, чаевые и дежурства живут отдельно; тариф
  получает терапевт, не платформа.

## Следствия

- +`apps/therapy` (модели, сервисы, админ с автотокеном), `api/v1/therapy.py`,
  миграции; `MeOut.is_therapist`; на фронте — `features/therapy/`
  (TherapyPane: каталог, кабинеты, инвайт; PayModal: QR + «Я оплатил»),
  роут `/therapy`.
- Риск «клиент нажал „Я оплатил“, но не перевёл» решён человеком: терапевт
  сверяет приход на свой кошелёк и только затем подтверждает. Платформа не
  арбитр споров — это осознанный предел зачатка.
- Автоматической сверки с блокчейном (phase 2) нет: подпись/метка платежа,
  верификация владения адресом — позже, по потребности.
- i18n-кап каталога поднят 560 → 640 (`apps/common/i18n_ui.py`,
  `flatten.test.ts` синхронно).
